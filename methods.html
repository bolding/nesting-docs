Methods

How the nesting works

Every level of a nest is an ordinary pyGETM simulation with its own grid, time step and processes. The nesting fills the halo zones where the levels overlap, and matches the fluxes through the faces between them, so that volume and tracer content are conserved. In 3D the levels may have different vertical grids. The names used on these pages (rim, ring, window, ...) are explained under Names used.

2D

Levels, halos and exchanges

Every level of a nest is an ordinary pyGETM simulation with its own grid, time step and subdomain decomposition. The nesting layer (pygetm.nesting, on the fork bolding/pygetm, branch nesting-mpmd) joins them by filling the halo zones where they overlap, and by matching the fluxes through the faces between them.

The exchanges

Load balancing

Because all models compute at the same time, the slowest model sets the pace. nesting-balance gives every model enough cores that all need about the same time per root step: it counts the wet cells each model computes, multiplies by its steps per root step, and picks the tiling per model. Subdomains that are all land, or hold only a child's hole that nothing reads, are removed and cost no core.

Launch: one MPMD component per model. nesting-balance prints the mpiexec command line for the balanced cores, or writes a Slurm job using srun --multi-prog; pinning to cores (--bind core) is optional.

mpiexec -bind-to core -map-by core \
    -n 7  python NEAB/models/neab_root/run.py        --nesting coarse.yaml ... \
  : -n 39 python NEAB/models/north_sea_baltic/run.py --nesting coarse.yaml ... \
  : -n 14 python NEAB/models/danish_straits/run.py   --nesting coarse.yaml ... \
  : -n 2  python NEAB/models/northern_little_belt/run.py ... : -n 2 python NEAB/models/northern_sound/run.py ...

The results are bit-identical to the single-program driver and independent of the process split.

3D

3D: exchanging between vertical grids that differ

In 3D, parent and child may use adaptive vertical coordinates, so their layers do not line up and may differ in number. A child column's depth also differs from its parent cell's, because of the child's finer bathymetry. The exchanges must conserve tracer content without assuming that layer k of the child matches layer k of the parent.

What each exchange needs

  • Rim (child → parent): the content of each parent cell equals that of its 3 × 3 child columns.
  • Ring (parent → child): consistent, accurate boundary values; the fluxes decide conservation.
  • Flux matching: the parent's flux through each face equals the child's, per tracer.

Options for the rim

  • A: average layer heights and contents of the ≤ 9 child columns by layer index, then remap once.
  • B: remap every child column, stretched linearly to the parent's depth, then add the contents.
  • B′: as B, but the upper 80 % of the column unstretched.
  • B″: B′ with concentrations by the child volume each parent layer receives, then the column content restored exactly.

  • For sigma layers A and B are identical: the stretched child layer k lands on layer k of the mean column. Both move the pycnocline by the stretch.
  • For GVC and adaptive layers A beats B: their upper layers sit at nearly the same depths in all nine columns, so averaging by index hardly mixes depths, while B's stretch moves them.
  • Only a linear stretch both conserves content and keeps a uniform field uniform. B″ gets both by forming concentrations by volume and restoring the column content afterwards; the correction is small because the volumes differ only deep down, where the stratification is weak.

  • The remap setup is shared by T, S and all FABM tracers: where every parent interface lies in each child column, and the volume per parent layer. It is about 80 % of B″'s cost for one scalar and has to be redone every exchange, because adaptive layers move.
  • The parent's layer heights go to the child once per sync, for all scalars.
  • The ring and the flux register need the same remap (one parent column onto each child column, and child face profiles onto parent faces), so the machinery is needed anyway; A only saves on the rim.
  • A compiled kernel (a merge of the two interface lists per column) should be 10–20× faster than numpy. That is the step before NEAB in 3D.

The 3D coupling as implemented

pygetm.nesting.baroclinic.NestedTracers3D is a coupler next to the 2D one (NestedBarotropic, which keeps coupling elevation and transports at every 2D step). By default all levels share the 3D time step: a child's split factor is its parent's times its time ratio, so every 3D step is a sync. A child can instead have a 3D step that is its parent's divided by a whole number R (below). Per 3D step of the parent:

ExchangeDirection, stageWhat is done
3D transportschild → parent, momentum_3d_transportsThe child's layer transports through its edge faces, remapped onto the parent's face layers (the parent's column total kept), replace the parent's at the window faces, before the parent's momentum diagnostics (vertical velocity, friction, advection, Coriolis) are computed from them. Both then move the same water through every layer.
Ring velocitiesparent → child, momentum_3d_transportsThe parent's layer transports at the faces around the child's ring faces (2 per face, linear across and constant along, as in 2D), remapped onto the child's face layers and shifted to the child's column total.
Flux registerchild → parent, tracerspyGETM's advection adds the tracer amount through every face and layer to arrays of the coupler. The child sends the amounts and the water through its edge faces; the parent remaps them onto its face layers (sums kept exactly), adds the r sub-faces and corrects the cell next to each face, layer by layer.
Rimchild → parent, tracersThe r × r child columns of each rim cell onto the parent's layers, concentrations by the volume each parent layer receives.
Ringparent → child, tracersThe parent's column onto the child's layers in each ring cell, plus the child's own vertical detail: its adjacent interior column, minus the same column through the parent's layers and back, limited to the range of the two.

The concentrations of the rim and the ring are remapped with every interface kept at its depth below the surface (only the bottom layer is cut or extended), so that flat isopycnals stay flat over a sloping bottom, and with a limited piecewise-parabolic reconstruction (PPM, Colella and Woodward 1984) inside each source layer, which carries a thin pycnocline from coarse onto fine layers 5–20 times more accurately than a constant. The remap runs in a compiled kernel in pyGETM (_pygetm.vertical_remap), 15 times faster than the numpy version, which stays as the fallback (PYGETM_NESTING_REMAP=numpy). The load balancer (nesting-balance) includes the 3D exchange per model. The amounts of the flux register and the transports are remapped with the stretch, which keeps their sums exactly. With all of it, a closed basin conserves its heat content to 1e-9 over 48 h, and a uniform field stays uniform to round-off (IDEAL). How it got there: exact rim content, the 3D transport sum, water per layer, a lake at rest.

3D sub-stepping

A child's split factor can be shorter than the default, so that R = parent's split × time ratio / child's split is a whole number larger than 1. The table above then runs once per 3D step of the parent, at the end of the child's R-th 3D step. In between, the child holds the ring: its concentrations, and the parent's layer transports, shifted at every 3D step to the column total of its own 2D ring. It adds up its tracer amounts and water through the edge faces, so that the parent's flux register and 3D transports see the whole of the parent's step. A level can be parent and child with different R. Results: IDEAL.

Grids

Curvilinear levels

pyGETM takes curvilinear grids (2D coordinates; dx and dy vary from cell to cell) and now includes the curvature term of the momentum equations, as legacy GETM does (changes to pyGETM). Can a curvilinear level, a fjord for instance, be nested in a spherical or Cartesian parent with the nesting as it is, or does it need a parallel path? Status: examined, not implemented in the nesting yet.

What the nesting depends on

  • Topology in index space. A child is a window of parent cells and a ratio r; child cell (j, i) belongs to parent cell (j0 + j / r, i0 + i / r). Rim, ring, hole, interface faces, active region and the exchange plans are all built in index space.
  • Each level's own metrics. Face volumes, face widths, cell volumes, restriction and the sponge use the metrics of the level's own grid. Nothing assumes regular metrics, and flux matching conserves volume and tracers with whatever metrics each side has.
  • Coordinates in few places. A level's coordinates are built from lon0 and dlon, and the active region's seed and barriers are located with them. Ring values are set per parent cell and face, and velocities are exchanged as grid components, without rotation.

The same path, with a conforming band

The exchanges only touch a band along the interfaces: the parent's rim (2 parent cells, each restricted from r × r child cells), the child's ring and halo (2 child cells) and the interface faces between them. If the child's grid in that band is exactly the parent's grid refined by r, every index relation the nesting uses is also a geometric one, both grids' U and V point the same way (no rotation), and the metrics are the parent's divided by r, as between regular grids today. Beyond the band the child's grid can follow the fjord freely: the nesting does not exchange there, and pyGETM handles the curvilinear metrics itself. So no parallel path is needed. A non-conforming child (overset coupling with geometric interpolation, intersecting faces for flux matching, rotated velocities) would be a different and much larger design, not needed for fjords, estuaries or harbours, whose grids can be made to conform at their mouth.

Forcing a curvilinear grid to follow the parent

Yes, in two ways. By construction, as in the IDEAL fjord: the grid starts with a straight section that is the refined parent grid, then bends; a check verifies it (15 conforming cells where 12 are needed with r = 5). For a grid from a grid generator: replace its first 2 r + 2 rows by the refined parent grid and blend into the generated grid over a transition zone. The blend costs some orthogonality there, which has to be checked. Either way the mouth sits on parent cell edges, which the layout needs anyway. The conditions can be checked at start-up, like the interface depth.

Spherical curvilinear grids

pyGETM, like legacy GETM, writes the equations in orthogonal curvilinear coordinates: only the length of a cell side along each grid line and how it changes from cell to cell enter. That holds on any smooth surface, the sphere included. The regular lon/lat grid is such a grid itself: four 90° corners in every cell although its latitude sides are not great circles, and the curvature term is the familiar u tan(lat) / R. A triangle with three 90° angles is the spherical excess: the angles of a polygon on the sphere add up to more than in the plane, by area / R². No global grid can be orthogonal and flat, but each cell is tiny against the Earth (1 km: 2.5 × 10-8 rad of excess) and the metrics act per cell. So a rotated-pole grid, or one that follows a coast, is a valid orthogonal grid on the sphere.

  • Limits: the grid must be (nearly) orthogonal, as in the plane; the cell area is dx × dy (the exact quadrilateral area is planar only); legacy grid_type 4 files are not read (building the points from the corners' lon/lat breaks at the date line and the poles). pyGETM's domain takes 2D lon/lat directly, as ocean-prep writes them. The curvature term is on by default for every lon/lat grid that is not rectilinear (rotated pole, coast-following) and off for regular lon/lat grids, as in upstream pyGETM.
  • Checked, a rotated-pole grid (0.05°, centred on 8° E 56° N on the rotated equator), once as a regular grid in rotated coordinates and once in geographic lon/lat: dx, dy and area agree to 10-12, the curvature coefficients to 10-16 (of 3 × 10-9).
  • Found and fixed: ocean-prep's rotated-pole transform was mirrored in longitude (one cell east in rotated lon went west), so its grids were left-handed: in pyGETM that gives a wrong grid angle (±90°), wrongly rotated wind and boundary velocities and the Coriolis force in the wrong sense relative to the grid. Fixed in ocean-prep (10 November 2026: the CF form, checked against cartopy); grids made with it before need regenerating. pyGETM now refuses left-handed grids. Also fixed (fork): pyGETM's grid angle on rotated lon/lat grids was taken in degrees without cos(lat), about 17 % too large at 56° N (2.69° against 2.26°), so wind and boundary velocities were rotated 0.4° wrongly there; now within 3 × 10-7°. Regular lon/lat grids are not affected. NEAB and DKm use regular lon/lat levels.

When the grids cannot be matched

The blend into the curvilinear grid costs orthogonality in its transition zone. That is too costly, or impossible, for an oblique mouth (the grid lines must turn by that angle within the zone: workable over a few km, with skewed cells), a long, curved interface (a child along a shelf edge or a whole coast), or a given grid that cannot be changed. To do in the nesting: an optional grid per level instead of lon0/dlon; seed and barriers located with the level's own coordinates; the start-up checks above; output across levels with the levels' coordinates; and in IDEAL a coast in the parent where the fjord attaches. The couplers, the exchange plans and the scheduler need no change.

Code

What the nesting changes in pyGETM

The nesting itself is a new package, pygetm.nesting: about 4,000 lines of Python with mpi4py, holding the geometry of the levels, the MPI exchanges, restriction, flux matching and the time loop. It attaches to each model through a small set of hooks in pyGETM's core: about 400 changed lines in twelve files. All of them are optional. A model without nesting runs exactly as before (the optional arguments default to nothing), with four exceptions: a bug fix in the transport damping, fixes that make a restarted run continue bit-identically, the curvature term on curvilinear grids (on regular longitude/latitude grids it is off unless asked for), and the grid angle of rotated or curvilinear longitude/latitude grids (fixed; left-handed grids are now refused).
