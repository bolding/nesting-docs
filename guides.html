Guides

How to run it

The tools of the nesting and its example setups, with the commands as they run today. The nesting itself is in the pyGETM fork (pygetm.nesting); the tools and setups below are in pygetm-nesting, which is not public yet. Paths are relative to its root.

1

The environment

Everything runs in one conda environment with the pyGETM fork built into it. pyGETM is compiled (Fortran and Cython), so after changing the fork's Fortran or _pygetm.pyx it has to be rebuilt; Python-only changes in pygetm/nesting need a reinstall too, since the fork is installed as a package, not in editable mode.

conda activate pygetm-nesting
export PYTHONNOUSERSITE=1          # keep ~/.local packages out
pip install -e ".[plot,dev]"        # pygetm-nesting itself: the nesting-* commands, lib/ as pygetm_nesting

# the fork (bolding/pygetm, branch nesting-mpmd), after changes
cd ~/source/repos/bolding/pygetm/python
pip install --no-deps --no-build-isolation .     # about 2 minutes
cd /tmp && pytest -q -p no:dash ~/source/repos/bolding/pygetm/python/tests/test_nesting.py \
                                ~/source/repos/bolding/pygetm/python/tests/test_nesting_vremap.py
  • Bathymetry with ocean-prep and the DDM (rasterio) run in the ocean-stack environment; nesting-bathymetry --run calls it itself.
  • The compiled 3D remap has a numpy fallback: PYGETM_NESTING_REMAP=numpy forces it (the simpler path for trying changes).
  • TPXO9 is found through --tpxo DIR or $TPXO9_DIR.

A hierarchy and its bathymetry

A nest is one YAML layout: the root's grid, and for every child its parent, its window in the parent's cells and its refinement.

config:
  min_depth: 5.0
  sources: {gebco: /data/cache/gebco/gebco_2026.nc}
  bathymetry: {rx0: 0.2}          # ocean-prep processing for all levels
neab_root:
  lon0: -20.0
  lat0: 42.0
  dlon: 0.2
  dlat: 0.125
  nx: 255
  ny: 196
north_sea_baltic:
  parent: neab_root
  istart: 60                      # window in the parent's cells
  istop: 253
  jstart: 52
  jstop: 192
  ratio: 3                        # cells per parent cell and side
  time_ratio: 1                   # steps per parent step (default: ratio)
  active:                         # the part of the window the child computes
    seed: [5.0, 56.0]
    barriers: [...]
  nz: 30                          # 3D: layers, 2D steps per 3D step (for the balancer)
  split: 10

Bathymetry of every level

nesting-bathymetry writes one ocean-prep bathymetry-regrid configuration per level, on the level's grid extended by the halo band and aligned with its parent's cells, and with --run runs them. A level's own source: key (gebco, emodnet, ddm) overrides --source.

nesting-bathymetry NEAB/config/coarse.yaml --outdir NEAB/Bathymetry/coarse --run
nesting-bathymetry DKm/config/dkm.yaml --levels limfjord_east,mariager_randers --outdir DKm/Bathymetry --run

For DKm, Denmark's Depth Model is first put on a lon/lat grid and completed with EMODnet outside Danish waters (in ocean-stack, for rasterio); levels then use it with source: ddm:

conda run -n ocean-stack python cli/nesting_ddm.py /data/DDM/ddm_50m.dybde.tiff \
    --emodnet /data/cache/emodnet/emodnet_-8.5400_14.0200_47.4750_62.0250_0p0020833333.nc \
    --region 7.0 13.6 53.8 58.3 --out /data/cache/ddm/ddm_emodnet_dkm.nc

Automatic thalwegs

nesting-thalwegs compares every level's grid with its fine source and finds what the grid closes: gaps (source water through the level's dry cells joining two basins) and shortcuts (joining two parts of one basin far apart around it). Through each it finds the path whose shallowest point is deepest, and the depth for each dry cell on it (a percentile of the source depths along the path there). Per level: a summary (<level>.json), ocean-prep waypoints and layout channels (<level>_thalwegs.yaml) and a map. --no-channels ignores the channels the layout already has, to test against them.

nesting-thalwegs DKm/config/dkm.yaml --out DKm/Bathymetry/thalwegs --figures DKm/docs/figures/bathymetry
nesting-thalwegs DKm/config/dkm.yaml --levels belt_sea --sill-min 3 --percentile 75 --out /tmp/thal

The DKm summaries are on the level pages linked from DKm. The thalwegs are applied by design_neab_hierarchy.py --write-bathymetry when the layout names the output (config: thalwegs: apply); the depths are set per layout and per level:

config:
  thalwegs:
    apply: DKm/Bathymetry/thalwegs   # nesting-thalwegs --out
    sill_min: 4.0                    # first search depth (m)
    percentile: 50                   # an opened cell: this percentile of the source depths along the path in it
    open_min_depth: 2.5              # ... and at least this deep
belt_sea:
  thalwegs: {{path_min_depth: 0.25}}  # this level searches down to 0.25 m (lagoons, Bodden, Roskilde Fjord)

The same search is part of ocean-prep's bathymetry-regrid (lib/bathymetry/closed_passages.py). There its passages become ordinary waypoint thalwegs, with the report and set_depth suggestions in fixes.yaml that can be accepted or rejected:

thalweg:
  closed_passages:                   # or: true
    sill_min: 4.0
    path_min_depth: 0.25
    percentile: 50
    fix_value_min: 2.5
    exclude_bboxes: [[9.3, 10.3, 54.7, 56.0]]   # e.g. children's windows

From LAT to MSL

EMODnet's depths are below the lowest astronomical tide (LAT); pyGETM's elevation is relative to mean sea level (MSL). ocean-prep's source_datum shifts the fine source by MSL − LAT before the block means. The shift is a lon/lat field, for example minus the lowest level of a two-year TPXO9 prediction (NEAB/scripts/lat_to_msl.py writes it). With mask_land: false the flats become sea above MSL. Denmark's Depth Model is already at MSL; in the merged DDM + EMODnet file only the EMODnet fill is shifted:

source_datum:
  offset: NEAB/Bathymetry/coarse_wadden_msl/msl_minus_lat.npz
  only_flag: {{file: /data/cache/ddm/ddm_emodnet_dkm.nc, variable: source, values: [2]}}   # 2 = EMODnet
  flats_max_height: 1.0

A bottom roughness map from EMODnet Geology's seabed substrate (Folk 7 classes, each given a z0), read by the NEAB/DKm models with --z0-map:

nesting-z0 --region -20 31 42 66.5 --res 0.01 --out /data/cache/emodnet_geology/z0_folk7_neab.nc
nesting-z0 --region -20 31 42 66.5 --set 3=0.02 5=0.02 --out z0_rough.nc     # other z0 per class

Cores per model: nesting-balance

All models run at the same time and meet at the exchanges, so the slowest sets the pace. nesting-balance counts the wet cells each model computes (its active region without its children's), multiplies by its steps per root step, picks pyGETM's tiling for each number of cores (subdomains that are all land or only a child's hole cost no core) and hands out the cores one at a time where they shorten the root step most. It prints the table and, if asked, the launch command.

nesting-balance NEAB/config/coarse.yaml --cores 64 --bathymetry NEAB/Bathymetry/coarse --plot balance.png
model                       grid      wet t_ratio steps      work cores   tiles subdomain land work/core      wait  busy
neab_root              255x196      16180       1     1  3.24e+04    11     3x8     33x66   13  4.36e+03       478   90%
north_sea_baltic       579x420      62742       1     1  6.27e+04    35     7x7     83x60   14  4.83e+03         0  100%
danish_straits         234x309      25984       1     1   2.6e+04    14     5x3     78x62    1  4.25e+03       583   88%
northern_little_belt    78x87        1555       3     3  4.66e+03     1     1x1     78x87    0  4.66e+03       169   97%
northern_sound          75x78        2011       3     3  6.03e+03     2     2x1     75x39    0   3.8e+03  1.03e+03   79%
cores used 63 of 64; wall time per root step = largest work/core = 4834

work: wet cells × steps per root step (× cost); land: subdomains removed; wait: time per root step spent waiting for the slowest model, in the same units; busy: the share of the root step a model computes.

Launching what it chose

# mpiexec, one component per model, ranks pinned to cores
nesting-balance NEAB/config/coarse.yaml --cores 64 --bathymetry NEAB/Bathymetry/coarse --mpiexec --bind core \
    --args '--nesting {config} --bathymetry NEAB/Bathymetry/coarse --out /data/kb/NEAB/runs/test'

# a Slurm job (srun --multi-prog)
nesting-balance NEAB/config/fine.yaml --cores 128 --bathymetry NEAB/Bathymetry/fine \
    --srun job.sh --partition short --time 02:00:00 --bind core --setup 'conda activate pygetm-nesting'

The run scripts default to <config dir>/../models/{level}/run.py (--script to change); {level} and {config} in --args are replaced.

3D and the cost model

The work per wet cell and 2D step is c_2d + nz (c_3d + c_fabm) / split; in 3D the exchange at the interfaces adds the vertical remaps of the rims (on the parent) and the rings (on the child) at every 3D step. The costs go into the layout:

config:
  ntracers: 2                       # 3D tracers exchanged (T, S + FABM's)
  costs: {c_3d: 9.0, exchange_3d_base: 0.45, exchange_3d: 0.2, ring_remaps: 4.0}
<level>:
  nz: 30
  split: 10                         # 2D steps per 3D step; a child: its parent's x its time ratio

The table then has the 3D exchange per model. The numbers above are IDEAL's on one machine, with the compiled remap; calibrate them for a setup and machine from measured runs:

# the 2D coupling's own work: per rim cell, per ring cell and step, per message (from runs at several splits)
nesting-balance IDEAL/config/ideal.yaml --cores 6 --bathymetry /tmp/ideal2d_bathy --fit-exchange RUN1 RUN2 RUN3 RUN4

# the costs per subdomain cell and step (all processes but the root's), then the cost factor per model
nesting-balance NEAB/config/coarse.yaml --cores 18 --bathymetry NEAB/Bathymetry/coarse --fit RUN1 RUN2 --calibrate RUN1

# c_3d and exchange_3d(_base) from a 2D run and coupled 3D runs with 2 and 14 tracers (IDEAL V7)
python IDEAL/scripts/calibrate_exchange3d.py --run2d /data/kb/IDEAL/runs/v7_2d \
    --run3d /data/kb/IDEAL/runs/v7g_ts:2 --run3d /data/kb/IDEAL/runs/v7g_12:14

# IDEAL: its analytic depth as level bathymetry files first
python IDEAL/scripts/ideal_bathymetry_files.py IDEAL/config/ideal3d_v5.yaml --out /tmp/ideal_bathy
nesting-balance IDEAL/config/ideal3d_v5.yaml --cores 12 --bathymetry /tmp/ideal_bathy --min-subdomain 6

# predict given splits instead of choosing one
nesting-balance NEAB/config/coarse.yaml --cores 64 --bathymetry NEAB/Bathymetry/coarse \
    --evaluate neab_root=7,north_sea_baltic=39,danish_straits=14,northern_little_belt=2,northern_sound=2

Running the models

Every level is an ordinary pyGETM run script; with --nesting LAYOUT it is one component of an MPMD launch, one mpiexec component per level (parents first). Everything a model writes goes to <out>/<level>/.

NEAB and DKm: 2D tides

L=NEAB/config/coarse.yaml; B=NEAB/Bathymetry/coarse; O=/data/kb/NEAB/runs/test
A="--nesting $L --bathymetry $B --out $O --constituents all --days 30 --z0 0.015 --hourly"
mpiexec -bind-to core -map-by core \
    -n 7  python NEAB/models/neab_root/run.py $A \
  : -n 39 python NEAB/models/north_sea_baltic/run.py $A \
  : -n 14 python NEAB/models/danish_straits/run.py $A \
  : -n 2  python NEAB/models/northern_little_belt/run.py $A \
  : -n 2  python NEAB/models/northern_sound/run.py $A
  • --constituents m2 or all (TPXO9 at the root's open boundaries), --spinup, --days, --start.
  • --z0, --z0-map FILE (nesting-z0), --z0-depth HREF (z0 reduced in shallow water); --z0 X after the common arguments of one level overrides it there.
  • --hourly: zt.nc; --fields MINUTES: zt, U, V, u1, v1 for nesting-boundaries; --boundaries FILE: the root's open boundaries from another model instead of TPXO9 (DKm from NEAB or CMEMS).
  • Output per level: zt.nc, m2.npz (M2 amplitude and phase), timing.json (per process: compute, nesting work, waiting; the input of --fit and --calibrate).

IDEAL: 2D and 3D

IDEAL/scripts/run_ideal.py builds the mpiexec command, runs it and summarises (volume, heat, timings). Arguments after -- go to every model; --layout-set and --level-set change the layout for one run (written to <out>/layout.yaml).

# 2D: tide, the sponge
python IDEAL/scripts/run_ideal.py --ranks channel=2,shelf=2,strait=2 --out /data/kb/IDEAL/runs/tide -- \
    --hours 48 --ramp-hours 3 --sponge-cells 3

# 2D: a closed basin with a bump, the strait level left out
python IDEAL/scripts/run_ideal.py --ranks channel=1,shelf=1 --drop strait --out /data/kb/IDEAL/runs/bump \
    --layout-set boundaries.west=closed -- --hours 12 --bump 0.5

# 3D with temperature, 10/15/20 layers (ideal3d.yaml); V5: a pycnocline over the slope; V6: plus a dye front
python IDEAL/scripts/run_ideal.py --layout IDEAL/config/ideal3d.yaml --script run3d.py \
    --ranks channel=2,shelf=2,strait=2 --out /data/kb/IDEAL/runs/t3d -- --hours 48
python IDEAL/scripts/run_ideal.py --layout IDEAL/config/ideal3d_v5.yaml --script run3d.py \
    --ranks channel=2,shelf=2,strait=2 --out /data/kb/IDEAL/runs/v6 -- --hours 48 --output-minutes 30 --dye 117 162

# the 333 m reference: one level everywhere
python IDEAL/scripts/run_ideal.py --layout IDEAL/config/ideal3d_v5_ref.yaml --script run3d.py \
    --ranks channel=32 --out /data/kb/IDEAL/runs/v5_ref -- --hours 48

3D options (IDEAL/models/ideal3d.py): --remap-scheme ppm|pcm, --vertical-map z|stretch, --no-ring-detail, --no-flux-matching-3d, --no-replace-transport-3d, --no-ring-velocities, --no-3d-coupling; --extra-tracers N; --profile (pyGETM's profiler per process). Per level a layout can set vertical: adaptive with config.adaptive parameters (not investigated yet).

Boundaries for another model

nesting-boundaries samples a run's output at another model's open-boundary points, the finest level with water at each point, in ocean-prep's layout (values at the model's own points, read with on_grid=True).

# 1. a NEAB run with hourly fields of every level
#    (as above, with --fields 60 in the common arguments, --out /data/kb/NEAB/runs/dkm_bdy)
# 2. the DKm root's and Belt Sea's boundaries from its north_sea_baltic and danish_straits levels
nesting-boundaries /data/kb/NEAB/runs/dkm_bdy/{north_sea_baltic,danish_straits}/fields.nc \
    --like DKm/config/dkm.yaml dkm_root,belt_sea DKm/Bathymetry \
    --write-points DKm/Bathymetry/dkm_bdy_lonlat.txt --out /data/kb/DKm/boundaries/neab_dkm.nc

This site

The pages are generated from tools/web/pages/*.py into a checkout of bolding/nesting-docs, which holds only the site:

python tools/web/site.py <checkout of bolding/nesting-docs>        # writes the pages and README.md, copies IDEAL's figures
cd <checkout> && git add -A && git commit -m "..." && git push

New results go on the example's page; anything that went wrong and was found or fixed goes into pages/issues.py, with a link from the example page (common.issue_links). A new example is one more entry in common.EXAMPLES.
